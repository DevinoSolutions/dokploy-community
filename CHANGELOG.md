# Changelog

Release notes for Dokploy Community Edition, newest first. The same notes, with the full credited change lists, are on [GitHub Releases](https://github.com/DevinoSolutions/dokploy-community/releases).

### Unreleased

**Stuck deployments are failed and free their queue slot, and a running deploy can be cancelled on a self-hosted instance** (T-7393). Three jobs sat `active` in the deploy queue for 5 hours and another deploy hung for 35 minutes in a registry push; with `buildsConcurrency` 4 a few such jobs block every deploy on the host. A watchdog now checks every running deployment once a minute and fails it when its log has had no new output for 20 minutes on two checks in a row (the log and the status are read again right before anything is stopped, and the deployment log only gets the watchdog line after that) (the log file's modification time, read on the host that holds the log: the Dokploy host, the serving server or the build server, against that host's own clock), or when it has run for more than 90 minutes. Both limits are settings, on by default: Settings, Deployments, "Stuck Deployment Watchdog" has the switch, the idle limit (minimum 15 minutes, so a quiet build step is not mistaken for a hang) and the wall time limit (minimum 15 minutes, and not shorter than the idle limit); through the API, `settings.updateDeploymentWatchdog` takes `enabled`, `idleMinutes` and `maxMinutes` (admin only, self-hosted only). Migration 0221 adds the columns to the web server settings with those defaults, so every existing instance has it on after the upgrade. When it fires it first writes `Watchdog: no log output for N min` (or `Watchdog: exceeded M min`) to the deployment log, then stops the work the way Kill build and Kill process do: the pid-file launcher of a build-server build or a rolling replace (so the rolling replace's trap and the transactional restore of the previous release run and the service ends in the state a normal cancel leaves), else `kill -9` of the recorded pid on the deployment's own server, else the generic `docker build` / `docker compose` stop, which it only uses when no other deploy runs on that host (it matches by command line and would hit them). A preview deployment that builds on a build server is not killed (its build has no handle the watchdog can use); the log says so. A deployment is only tied to the queue job of its service when it was created after that job started, so a leftover `running` row of an older deploy never stops a healthy build. A `running` row that no queue job runs (left over from a restart) is only marked failed: nothing is signalled for it except through the pid-file launcher, which checks the pid and its start time, so an unrelated `docker build` on the host is never hit. The slot of a job is freed even if marking its row or writing the audit entry fails. A deployment that was cancelled by a person stays cancelled, and nothing is logged or notified as a watchdog failure when the row was not changed by it. Once the job has ended it sets the deployment to `error` with the reason, writes `Watchdog: marked failed`, sends the existing deployment-failed notification (once: not again if the deploy flow had already failed it) and records a `watchdog_fail` entry in the cancel trail with the system as the actor. A job that has not ended 10 minutes after it was stopped (it is hung where no signal reaches) has its queue slot and its journal row released by force after its row and service were settled, the service goes to `error` if it is still `running`, and the log says so. When nothing could be signalled (no handle at all), the service's group lock is kept, so a second deploy of that service does not start next to a process nobody could stop: it stays blocked until that process ends, or for at most max(2 x the wall limit, 3 hours) after the release, when the watchdog drops the lock with an error in the server log, a line in the deployment log and a `groupLockDropped` audit entry; before that, a stop that found no handle only because other deploys run on the host is tried again on every sweep, so it works as soon as they have ended. The log and the audit entry say all of this. A job released by force cannot write its late results: its deployment and service status writes are ignored (deployment writes are also refused by deployment id); the same release applies to a job left `active` for 5 minutes after its deployment ended, or for longer than the wall limit with no deployment at all. A service can be excluded so its deployments are never auto-failed (and its queue slot never released by force): turn on "Exclude from the stuck-deployment watchdog" in the service's Advanced tab, for applications and composes (anyone who may update the service can flip it, not only admins; API `application.setWatchdogExclusion` / `compose.setWatchdogExclusion`), or let an admin pick services in the settings card (`settings.addDeploymentWatchdogExclusion` / `removeDeploymentWatchdogExclusion`); both edit the same list with one atomic SQL update (two edits at once cannot lose an entry), kept on the web server settings because the application table has no room for another column; an admin can only add or remove services of their own organization. A malformed entry in the stored list is skipped on its own and the valid ones stay in force. Nothing is excluded by default. Separately, `application.cancelDeployment` and `compose.cancelDeployment`, which were Cloud-only ("Deployment cancellation only available in cloud version"), now work on self-hosted: they keep the `deployment:cancel` permission and the audit entries, stop the running deployment through the same machinery, and the Cancel button of an active job in the deploy queue table is shown on self-hosted too (previews are not cancelled from it). The slot is freed when the job has ended, not by force, since a restore of the previous release may still be running; the answer says whether it is free yet. Not covered: a per-server override of the limits, and a stop that leaves no handle (a local application build with no pid while other deploys run on the same host) can only be released by force after the 10 minutes, so its process may keep running on the host until it ends.

**Nightly Docker cleanup moves from 23:50 container-local time to 04:00 UTC, is configurable, and waits for deployments** (T-7344). The cleanup time was hardcoded to `50 23 * * *` in the container's local time, and on 2026-10-22 it deleted a freshly built image in the middle of a registry push. Every host now has a `dockerCleanupCron` setting (a 5-field cron expression, always read in UTC whatever the container's TZ is; default `0 4 * * *`) on the web server settings and on each remote server. Migration 0220 adds the column with that default, so every existing host moves off 23:50 automatically on upgrade. To change it: in the UI, open the Docker cleanup toggle (Settings, Web Server for the Dokploy server; the server's actions menu or the Edit Server dialog for a remote or build server) and pick the hour (UTC); through the API, send `dockerCleanupCron` to `settings.updateDockerCleanup` (with `serverId` for a remote server) or to `server.create` / `server.update`. A schedule that would run more often than hourly (for example `* * * * *`) is rejected, and changing the schedule cancels the old job and schedules the new one right away. When the job fires it first checks the host for running or queued deployments, counting builds that run on a build server against that build server: if any are active it logs `Docker cleanup deferred: N deployment(s) active on <host>`, checks again every 15 minutes for up to 3 hours, and gives up for that night if the host is still busy (the next scheduled run tries again). The check is repeated between the prune commands, and if a deployment started meanwhile the remaining prunes are skipped and `Docker cleanup aborted mid-run: deployment started on <host>` is logged. A schedule whose day never occurs in its months (`0 4 31 2 *`) is rejected, and a stored one that never fires falls back to the default instead of leaving the host uncleaned. Not covered: rollbacks and database deploys have no deployment row or queue journal entry, so the guard does not see them. The 300 s "proceed anyway" timeout inside `dockerIdleExec` (the wait for other docker commands to finish) is unchanged; it is a likely way the 2026-10-22 incident got through. The Cloud jobs service is unchanged, and the hour picker is hidden there.

**undici 6.29.1 and 7.30.1 for GHSA-xjj6-f33q-929c** (T-7450, security audit gate). The pnpm overrides now move undici `>=6.0.0 <6.29.1` to 6.29.1 and `>=7.0.0 <7.30.1` to 7.30.1 (it was 7.29.1), fixing the high advisory reported by Dependabot (#499, #500). Lockfile only; no code changes.

**A compose with "Create env file" off no longer gets host paths from a `.env` the check never read** (T-7160, security, follow-up to T-7142 and T-6822). With "Create env file" off, Dokploy writes no env file and Compose reads the `.env` of the project directory, which the repository brings. The volume and host-path check did not look at it and let a bare unresolved variable through, so a committed `.env` with `DIR=/var/lib/docker/volumes/<another tenant's volume>/_data` and a compose with `volumes: ['${DIR}:/data']`, `build: ${DIR}`, `env_file: ${F}` or `secrets: {s: {file: ${F}}}` passed the check while Compose used the victim's path. The check now reads that `.env` from the host where the compose runs (the compose's server, after the clone and patches, or before the write for a raw compose, and again for Start and on save), parses it the way Compose does (comments, `export`, quotes, multi-line quoted values, `$VAR`, `${VAR:-d}`, `${VAR-d}`, `${VAR:+a}`, `${VAR:?e}` and `$`, with the values referring to earlier lines) and judges every host path with the values it gives: `${DATA_DIR}:/data` is still fine when the file says `DATA_DIR=./data`, and refused when it says `DATA_DIR=/var/lib/docker/volumes/x`. The directories it can come from are all read (the compose's own and the code directory; a custom command's `--project-directory` and file directories, also with "Create env file" on, because Compose then reads a `.env` Dokploy did not write), and the compose is checked with each of them. No `.env` at all means the variables are unset. Anything that cannot be read or understood is not trusted: a `.env` that cannot be read, that has a line or a quote the check does not understand, that sets a variable twice or sets `COMPOSE_ENV_FILES`, or is over 1 MB, and any custom command with `--env-file` (the file is not read). In that case a host path that contains any variable is refused, a default (`${X:-./ok}`) included, because the file may set the variable; the same for the source of a short-syntax volume (`${VOL}:/data`, which cannot be told from a path) and for a remote-looking build context (`github.com/${ORG}/app`). The message says that the env file could not be read and points to "Create env file". Also fixed: a `..` that is followed by `}` (a default such as `${A:-..}${B:-/..}`) is a climb too, so `github.com/${A:-..}${B:-/..}...${I:-/var/lib/docker/volumes/v}` is no longer taken for a remote build context, and the same in a `dockerfile` next to a remote context. Upgrade note, for composes with "Create env file" off: nothing changes when the `.env` next to the compose file (or none) gives safe paths; a compose is refused at its next deploy, redeploy, Start or save only when its `.env` sets a host path into `/var/lib/docker/volumes` (or `/`, `/var`, `/var/lib`, `/var/lib/docker`), or when the `.env` is unreadable or not understood, or the command passes `--env-file`, and a path in it has a variable. Fix: turn on "Create env file" (Dokploy's own `.env` is then the only one Compose reads, and the committed one is not used), simplify or remove the odd `.env` lines, or write the paths out in the compose file. The environment is taken per command of a custom command: `docker compose` reads the `.env` (with a stack's staged variables over it, also for a stack-type compose), and `docker stack deploy` is checked with the staged variables and with none. Every docker command of a chained custom command (`docker compose ... && docker compose ...`) now runs under `env -i PATH HOME` (with a stack's staged variables), including the restore after a failed deploy: only the first used to, so the others ran with the Dokploy process's or the ssh session's whole environment, and a `${SERVER_VAR}` in a compose reached the containers (T-7281, folded in); the check also reads the `.env` alone when a stack chains commands. A `.env` with a control character or non-ASCII white space (NEL U+0085, NBSP and the like, which Compose trims and the check does not) is not trusted. The `.env` is read as a regular file of at most 1 MB (a FIFO, a device or a larger file is not trusted, and a remote read has a time limit), and a refusal of a volume name that came from a variable shows the compose's text, not the value. Not covered, and tracked separately: the build server clones the repository again for its build, so a branch moved between the two clones is not seen (as for the compose file itself); a `--project-directory` that points at another service's code directory; and a symlinked `.env` is followed by Compose and by the check alike.

**Remote commands detect a dead SSH connection instead of hanging** (T-7441). A command on a build server prints nothing while a build writes its output to a file, so when the link to the server went half-open the SSH channel never closed and the call never returned: a deploy built on a build server stayed `running` for close to an hour after its script had finished. Remote commands now send SSH keepalives (every 10 seconds, giving up after 3 misses) and fail with a clear error when the connection drops before the command finishes, which also releases the deployment queue slot.

### New in v0.30.8-community.32

No database migrations in this release.

**Build-server composes: a failed compose config is logged, and an image removed mid-build is rebuilt** (T-6283, [#439](https://github.com/DevinoSolutions/dokploy-community/pull/439)). The `docker compose config` step on the build server is not streamed (its stdout is the resolved environment) and its error was never written to the deployment log, so a compose that does not resolve, such as a required `${VAR:?}` with no value, failed in about 12 seconds with an empty log and a rollback. Its stderr (the reason, not the configuration) is now written to the log. Separately, the push step failed with `The build did not produce image ...` on long builds: images built early in the build were missing by push time, which coincided with image-prune activity on the build host whose source has not been identified. The push step now rebuilds a missing service once from the layer cache and logs a warning, then goes on.

**Manual deploy coalescing follow-ups** (T-6233, [#443](https://github.com/DevinoSolutions/dokploy-community/pull/443), after [#437](https://github.com/DevinoSolutions/dokploy-community/pull/437)). Three changes. The first two apply only with remote builds enforced; with the policy off, the only change is that manual Deploy and Redeploy clicks on the same service are handled one after the other (the third item).
- The Deploy and Redeploy buttons and API calls for an Application now coalesce waiting deploys like the Compose ones do: a request is folded into the application's oldest waiting job of the same kind and the other waiting duplicates are dropped and audited. PR previews are never touched, a redeploy is never merged with a deploy, priority requests skip it, and Cloud is unchanged. The newest request wins, as for a webhook push: when a manual deploy folds into a waiting webhook job that carries a pinned image, the job takes the manual request's data, so the pinned image is dropped and that deploy builds from source.
- A drop caused by a manual click is now recorded in the cancel audit trail under the user (or API key, or OAuth client) who clicked, since the click can replace another user's waiting job. Drops caused by a webhook push are still recorded as the system.
- Two quick manual clicks on the same service are now handled one after the other, so a second click can no longer slip in while the first is still writing its audit rows and leave an extra duplicate in the queue. A click waits at most 60 seconds for the one ahead of it. A webhook push racing a click is not covered and can still leave one duplicate, which the next coalescing pass folds.

**Web-server backups are owner/admin-only with organization-scoped destinations and backup lookups** (T-6800, [#458](https://github.com/DevinoSolutions/dokploy-community/pull/458), security). Backups of the Dokploy instance itself (databaseType `web-server`) belong to no service, so their create, update, run and restore paths skipped the permission and organization checks, and a service backup row could carry a second service id that was never permission-checked; a plain member could schedule an instance backup to a bucket they control. Instance backups now require the organization owner or admin (the same gate as the instance-level settings), and a backup must target exactly one service of the kind its type says. Destinations are organization-checked on create, update and restore (an empty `databaseId` no longer falls back to an unscoped destination), by-id backup routes treat a backup or service of another organization like a missing one, a backup's database type cannot be switched to or from `web-server`, and the per-service manual run routes only accept a backup of their own service type. The run path (cron and manual, including the cloud scheduler) refuses a row that targets several services or the wrong kind, and the instance backup refuses a destination outside an organization its creator administers before anything is zipped or uploaded. Existing web-server backups created without a creator, or whose creator is no longer an owner or admin of the destination's organization, stop running and show a failed run until an owner or admin re-saves (re-attributes) or deletes them; any owner or admin of the destination's organization can see, update, disable or delete such a row. Volume backups get the same service binding: every service id on a new row is permission-checked, an update cannot re-point a row at another service, and a volume restore checks the target service and only accepts volume names recorded on that service's volume backups or mounts (defence in depth; the names themselves are still user-chosen). The application update input now validates branch names with the compose validator, and run-path destination tests cover MySQL, MariaDB, MongoDB, libSQL and compose.

**Volume names are bound to the service's own volumes** (T-6808, [#459](https://github.com/DevinoSolutions/dokploy-community/pull/459), security). A volume backup, a restore and a named mount took any Docker volume name on the host, so a member with volume permissions on their own service could back up another organization's database volume to their own destination, restore over it, or mount it. Creating or updating a volume backup or a named mount now accepts only a volume named after the service (`<appName>-...` or `<appName>_...`, which covers a database's `<appName>-data` and a compose stack's `<appName>_<volume>`), one the service already mounts, or, for organization owners and admins only, an outside volume that another service of the same organization already mounts or that the service's own compose file declares. Dokploy's own volumes and volumes another organization's services claim on the same server are always refused. Every volume backup run (scheduled, manual and policy) checks the name again and fails closed as a failed run with a notification, and restores check it too; mounts can no longer be re-pointed at another service. Restores run only on the server of the service, and volume backups of databases now run on the database's own server (they used to run on the Dokploy host whatever the database's server).

**Registry, git provider and SSH key ids are checked against your organization, and the profile update takes only profile fields** (T-6895, [#461](https://github.com/DevinoSolutions/dokploy-community/pull/461), security). Three gaps. First, a service update or a save of a git source accepted any registry, git provider or SSH key id without checking whose it was. `application.update` and `compose.update` (registry, build registry, rollback registry, GitHub, GitLab, Bitbucket, Gitea and the custom-Git SSH key) and the application `saveGithubProvider`, `saveGitlabProvider`, `saveBitbucketProvider`, `saveGiteaProvider`, `saveGitProvider` and `saveDockerProvider` calls now refuse an id that belongs to another organization, or that does not exist, with the same "not found" error, before anything is written. Before, a member with permission to edit their own service could point it at another organization's registry or git token and have the next build push, pull or clone with those credentials. Leaving an id unset (or clearing it) still works. Second, `user.update` spread whatever the caller sent onto their own user row, so a user could write columns such as `emailVerified`, `banned`, `twoFactorEnabled` or the licence and billing fields. It now takes only the profile fields the Account page sends (email, image, first and last name, the impersonation switch) plus the password change, and ignores everything else; changing a password with the current one works as before. Third, updating a GitHub, GitLab, Gitea or Bitbucket provider needed only the permission to add providers, so any member could rewrite a provider someone else connected, and with it the token or endpoint every deploy using it clones with. Only the user who created the provider, or an organization owner or admin, can update it now; other members get a forbidden error. Upgrade note: a service that already points at a registry or provider from another organization is not touched at upgrade and keeps deploying, but the next update or save of that service that includes the id fails until the id is replaced with one of your own.

**Git provider access, deploy-time organization re-check and duplicate refusal** (T-6902, [#463](https://github.com/DevinoSolutions/dokploy-community/pull/463), security). Follow-up to T-6895, three gaps. Because reads come back blank, a write that sets a secret field to an empty string is refused unless `allowEmptySecrets: true` is passed with `dokploy:admin` (`saveEnvironment` replaces the whole env; `envKeys` now exists for the six database services too). Not covered: a literal secret inside a Compose file, a command, a deploy hook, a schedule command or a file mount, the Traefik config reads, deployment logs, a secret under a field with another name, and admin credential reads, which stay raw; the dashboard's own `environment.one` and `project.one` are unchanged.

**The Docker page and file routes only act on containers the caller can reach** (T-7051, [#471](https://github.com/DevinoSolutions/dokploy-community/pull/471), security, follow-up to T-7030). `docker.restartContainer`, `startContainer`, `stopContainer`, `killContainer`, `removeContainer`, `uploadFileToContainer`, `listContainerFiles`, `readContainerFile`, `writeContainerFile`, `deleteContainerFile` and `getConfig` took a raw container id and only needed `docker:read`; on the shared local host (no `serverId`) a holder could restart, stop, kill or remove any container and read or write files in it (writing files is a way to run code), including other organizations' containers and Dokploy's own. A given `serverId` was only checked to be in the organization, not that the member may use that server. Each route now resolves the id with a single `docker inspect` to one full container id plus its labels, maps the labels to the services behind it (a preview deployment counts as its parent), and requires the caller to read every one of them in their organization on that same server, exactly like the terminal and logs sockets; the command then runs on the full id, locally or over SSH. A container that backs no service (Dokploy, Traefik, its database, an unlabelled one) is for owners and admins only, and every refusal is the same `NOT_FOUND` "Container not found". Routes that change a container or its files (restart, start, stop, kill, remove, upload, write, delete) also need `deployment:create` on each service behind it, the gate that starts and stops the service itself (the `docker` statement has no write action, so `docker:read` stays the entry check; owners and admins pass `deployment:create` like every enterprise statement). Every route of the router now checks that the caller can use `serverId` (for a member, a server they were granted) instead of only that it is in the organization. The member container listing keeps the containers that still exist when one vanishes mid-listing.

**Volume-name binding reaches deploy, rebuild, transfer and the Docker volumes API** (T-6822, [#460](https://github.com/DevinoSolutions/dokploy-community/pull/460), security). A stored mount could still carry a volume name that the T-6808 rules would refuse. Deploy now fails (log and failed deployment, same refusal text) when a mount names a reserved `dokploy*` volume, a name that is not a plain volume name, or one another organization claims on the same server. A database rebuild with such a mount is refused before the service or any volume is touched. A transfer is refused before anything is read or written, checking both the source and the target server. Owners' and admins' own outside-named mounts keep working. The `dockerVolume` router (list, size, config, browse, read, write, delete, remove) is now owner/admin only (owners and admins still reach host-global volumes), and the Docker page hides the Volumes tab for everybody else. The `update` procedures of application, compose and every database no longer accept `environmentId` or `appName` (only `move` changes the environment, and `move` checks that the target environment belongs to the active organization); `project.update` no longer accepts `organizationId`, `environment.update` no longer accepts `projectId`, and `registry.update` no longer accepts `organizationId` and checks its login server; `server.update` checks that `sshKeyId` belongs to the active organization; and the GitHub, GitLab, Gitea and Bitbucket provider updates check that the provider belongs to the active organization (they previously re-assigned any provider id to the caller's organization). `project.duplicate` checks that every selected service belongs to the active organization, libsql checks its appName for uniqueness after the suffix is added, and the appName suffix uses `node:crypto`. **A compose file can only mount its own volumes, or ones nothing else uses** (T-6822, [#462](https://github.com/DevinoSolutions/dokploy-community/pull/462), security). A compose file could name any Docker volume on the host: a top-level volume with `external: true`, one with `name: <other volume>` (which works without `external`), and a service volume pointing at it. A member who can edit their own compose file could read or write another service's or another organization's data that way, and a "fresh volumes" deploy (`down --volumes`) removes a non-external volume that carries `name:`. Deploy, redeploy, preview deploy and Start now work out the Docker volume name of every named volume the final compose file mounts and refuse the deploy, before anything is built, torn down or started, when that name is reserved (`dokploy*`), is claimed on the same server by another organization (a mount, a volume backup, an `<appName>` name prefix, or the compose file of another compose that has a finished deployment), or is claimed by another service of your own organization in the same ways. The refusal is written to the deployment log, and the server log names the conflicting rows. The names are resolved the way Docker does it: an explicit `name:` is used as is, `external` (a boolean, a string such as `"TRUE"`, or a `${VAR}`) without `name:` uses the key, and anything else is `<appName>_<key>` (`<stackName>_<key>` for a stack). The checked file is the one that is deployed, so randomize and isolated deployments (which rename keys) and `${VAR}` values from the service environment are applied first; a variable that is set to an empty value counts as set for Docker Compose and as unset for a stack, as Docker sees them. A compose's own `<appName>_...` volumes, its own mounts and volume backups, anonymous volumes and volumes nothing records still work. For a raw compose file the check also runs when you save it, and a compose transfer applies the same check to the volumes its file names. Another compose's `name:` or `external` volume is only visible through its stored (raw) compose file, and only once that compose has a deployment with status done (the compose status, which is no longer settable through `compose.update`, does not count), so a compose that was only saved, or whose deploys were refused, cannot lock another one out. A declaration never evicts a record: a service that already has its own mount or volume backup row for a name is not refused for it because of another compose's file. A volume name another organization's compose declares can no longer be added as a new mount or volume backup. Limits, left as follow-up T-6919: declaring a volume name that nothing records yet before its owner uses it is first-come and at worst denies the owner that name; a compose from a git source declares nothing to this check, because only a stored raw compose file is read. A bind mount of Docker's own volume directory (`/var/lib/docker/volumes`, or a path under it, also through `..`, a variable or a local-driver volume with `driver_opts.device`) is refused, because it is a named volume by another name. A custom compose command is read too: a command that starts containers must name its compose file with `-f` (`-c` for a stack), and extra `-f` override files are read and checked together with the deployed file. A refused deploy of a fetched source puts the previous release's compose and `.env` back, so Start cannot run the refused file. The check cannot see through a few features, so a compose file that uses them is refused with a message that says which: `include` of another file, a service `extends` from another file, `volumes_from` a container, and a volume name, `external` value or mount source that depends on a variable Dokploy does not provide (any variable at all when "Create env file" is off). Upgrade note: these fail their next deploy, redeploy or Start until fixed: two composes (of the same or of different organizations) that share a volume through `external` or an explicit `name:`; a compose that mounts a volume another service uses; `name: ${VAR}` and similar with "Create env file" off; `include`, file `extends` and `volumes_from: container:`; and custom commands that name no compose file or an unreadable one. To keep sharing a volume between composes of one organization, an owner or admin adds a mount (type volume) or a volume backup with that volume name to EACH compose that uses it; a compose that records the volume itself is not refused for it, and composes of other organizations can never share. A running stack is not touched at upgrade. General host bind-mount policy beyond Docker's volume directory and its parents is still open.

**Compose volume check: binds of the directories above Docker's volume storage, `compose run -v`, and variable bind sources** (T-6919, [#470](https://github.com/DevinoSolutions/dokploy-community/pull/470), security). Follow-up to the compose volume check (T-6822). A bind mount of a directory that contains Docker's volume storage reaches every volume on the host just like a bind of the storage itself, so a compose file that binds `/`, `/var`, `/var/lib` or `/var/lib/docker` is now refused at deploy, redeploy, preview deploy and Start, with a message that names the path. Paths are normalised first (trailing and repeated slashes, `.` and `..`), a relative path is resolved from the compose's own directory, from `--project-directory` and from the directory of any file the command names, and the rule applies to short and long syntax, to the `device:` of a local-driver volume, to override files of a custom command, and to `/proc/<pid>/root` and `/proc/<pid>/cwd` (recognised by their shape, also when a `..` would collapse them). It is the same for owners, admins and members, as the storage check already was. A custom command with `docker compose run -v SOURCE:TARGET` (or `--volume`, in any of the forms the CLI reads) is now checked too: a path source follows the rules above, and a volume name goes through the same claim check as a name in the compose file (a name the compose declares is its own key; a name no file declares is the Docker volume of that name); a shell variable, backtick or pattern character in the value is refused because it cannot be known, and so is a line that has a glob or a shell operator other than `&&` next to a `docker compose run` (the shell could rewrite it). A command with its own `--env-file` makes the compose's variables count as unknown. A variable, substitution or pattern in its `--project-directory`, compose file or `--env-file` is refused, since the path it leads to cannot be known. A short-syntax volume was cut at the first colon before its variables were resolved, so `${DATA:-/srv}:/data` was never resolved and a colon brought by a variable (`${X:-/:/h}`, or `${VOL}` holding `/:/h`) could hide a bind of `/`. The whole entry is interpolated and split after that now, as Compose does, and an entry that is only variables is refused when they cannot be resolved. With "Create env file" off, a bind source that is already inside Docker's volume storage by what is written before the variable (`/var/lib/docker/volumes/${NAME}`, or `/var/lib/docker/${NAME}`) is refused, and so is any `..` segment in a source that still depends on a variable that cannot be resolved (`${HOME}/../..`, `${A}${U:-/../..}`, `${X:-${HOME}/..}`), wherever it sits, with one exception: a lone variable with a literal default (`${DATA_DIR:-../data}`) is judged as that default, so `${X:-/}` is still refused (a `..` that a known variable brings next to an unknown one, such as `${HOME}/${UP}` with `UP=../..`, is seen by substituting the known variables and emptying the others). The values of the Environment tab are expanded the way Compose expands a `.env` first (a value that refers to `$B` or `${B:-x}` is what it resolves to, `$$` stays a literal `$`), and a value that refers to a variable defined on a later line, to itself, or through `${X:?}` cannot be followed, so a bind source that uses it is refused; a source that is only a variable (`${DATA_DIR}:/data`) stays allowed, as before, and every declared volume is checked instead. Upgrade note: a compose that binds `/var/lib/docker`, `/var/lib`, `/var` or `/` fails its next deploy, redeploy or Start until the bind is narrowed. Not covered, and left as follow-ups: a symlink that only exists on the host (the check never touches the host), volume name squatting, composes whose file comes from git, the retention window of the volume record, and the cost of the checks.

**A custom compose command can only run `docker compose` or `docker stack`, and cannot reach other services' volumes through them** (T-7055, [#473](https://github.com/DevinoSolutions/dokploy-community/pull/473), security, follow-up to T-6919). The compose volume check read the volumes of a custom command only when it was `docker compose`; the command runs as `docker <command>`, so one that started with something else, such as `run -v /var/lib/docker/volumes/<another service's volume>:/x alpine`, `run --mount type=bind,src=/var/lib/docker,dst=/x alpine`, `run -v <another service's volume>:/x`, `--volumes-from`, `cp` or `exec`, was not checked, and mounted or read another service's volume or container. A custom command is now refused when it runs any docker command other than `compose` (or `docker-compose` when chained) and `stack`, first or chained. It runs at deploy, redeploy and preview before the compose is built or started, which for a git source is after the clone. Besides that: only the compose subcommands a service needs are allowed (`up`, `down`, `ps`, `logs`, `pull`, `build`, `stop`, `start`, `restart`, `run`, `exec`, `create`, `rm`, `kill`, `pause`, `unpause`, `top`, `images`, `port`, `version`, `wait` and `config`) and for a stack `deploy`, `rm`, `ps` and `services`, so `compose cp`, `export`, `config -o FILE`, `ls` (it lists every project on the host) and `watch`, `up --watch` and `up -w` (they sync host paths named in the compose file) are refused; the docker options that point at another daemon, context or config (`-H`/`--host`, `-c`/`--context`, `--config`, `--tls*`) are refused, also chained; the compose file, `--env-file`, `--env-from-file` and `--project-directory` may not lead into Docker's volume storage; and `docker compose run` with `--mount` or `--volumes-from` is refused (even after the service name, fail closed), because those mounts are not read; `-v` is still checked as before. The restore that runs after a refused deploy, or a cancel, no longer re-runs a custom command the check refuses: it brings the previous release's files back up with the default command, and the deploy log says the command was left out (the check judges the whole compose, so a refused compose file leaves it out too). The default command and custom `docker compose` / `docker stack` commands are unchanged.

**Compose file host paths other than `volumes:` get the same Docker-volume-storage check** (T-7142, [#474](https://github.com/DevinoSolutions/dokploy-community/pull/474), security, follow-up to T-6822, T-6919 and T-7055). The compose volume check read the `volumes:` entries of a service only, but Compose reads several other keys from the HOST, so a path under `/var/lib/docker/volumes/<another service's volume>/_data`, or a directory above it, could send another tenant's data into a build context or image, a container environment, or a mounted secret or config, and the default `docker compose up -d --build` does all of that. These keys now go through the same normalisation, parent rule, unresolved-variable rules and worst-case substitution as a bind mount source, resolved from the compose file's directory (and `--project-directory`) like a relative bind: `build` (the string form, `context`, a `dockerfile` that leaves the context or is absolute, `additional_contexts` in the map and list forms including `oci-layout://` directories, `ssh` key files (also several, comma-separated), an `oci-layout://` or `file://` context, and the `src` / `dest` directories of `type=local` `cache_from` / `cache_to`, read as CSV the way buildx does, so a quoted `"dest=..."` or `"type=local"` is seen, and an entry that only mentions `local` or has a quote is checked as well), `develop.watch[].path`, `env_file` and `label_file` (a string, a list, or the `path:` form), and the `file:` of the top-level `secrets` and `configs`. A refusal names the key and the path. A remote build context (`https://`, `http://`, `git://`, `ssh://`, `git@`, `github.com/`, the prefixes Compose itself recognises) is not a host path and is left alone with its dockerfile, unless the value has a `..` segment (`github.com/../../x`, `https://x/../..`): Compose keeps it as written and a directory of that name makes it a local path, so it is checked like any path. The same goes for a dockerfile that climbs out of such a context. Also left alone: `service:` and `docker-image://` additional contexts, `secrets.<name>.environment` and `content`, and an `ssh` agent (`default`). Legit relative paths (`./app`, `../shared`, `.env`, `./secrets/token`) are unchanged. The check runs at deploy, redeploy, preview deploy, Start and on save, like the volume check. Upgrade note: a compose whose build context, env file, secret or config is `/`, `/var`, `/var/lib`, `/var/lib/docker` or inside `/var/lib/docker/volumes` fails its next deploy until the path is narrowed. Not covered, and left as follow-ups: a symlink that only exists on the host, `provider.type` and `credential_spec` files, a bare unresolved variable as a whole path with "Create env file" off (the same gap as for volumes), and `include` and `extends` from other files (still refused as before).

### New in v0.30.8-community.30

**Opt-in rolling replace for Compose services** ([#399](https://github.com/DevinoSolutions/dokploy-community/pull/399), issue [#374](https://github.com/DevinoSolutions/dokploy-community/issues/374) item 4). Off by default. A plain `docker compose up -d` stops the old container before the new one exists, which leaves a window with no backend. With rolling replace enabled for a service, the new image is built or pulled first, a second replica is started next to the old container, and the old container is stopped and removed only after the new replica reports healthy and a drain delay has passed. A replica that never becomes healthy is removed and the old container keeps serving.
- Enable it per service on the Compose Advanced tab, in the Rolling replace card. The card lists each service with its eligibility and the reasons it is refused.
- Health timeout 10-900 s (default 120) and drain delay 0-120 s (default 5). The health wait is raised automatically to cover the service's healthcheck (`start_period + retries x (interval + timeout)`, capped at 900 s), so a healthcheck that only sets `test` is no longer refused; only one that cannot settle within 900 s is ([#400](https://github.com/DevinoSolutions/dokploy-community/pull/400)).
- Refused on save and again at every deploy for services with `container_name`, a published host port, host or shared network modes, `scale` or `deploy.replicas` other than 1, static addresses, no usable healthcheck, or datastore images such as databases and queues. Only `docker-compose` type composes qualify; stacks, custom commands, fresh-volume deploys and previews never roll.
- Adds the nullable `compose.rollingReplace` column (migration 0217). With it unset or disabled, deploy scripts are byte-identical to the previous release.
- Design and decisions: `docs/design/compose-zero-downtime.md` ([#396](https://github.com/DevinoSolutions/dokploy-community/pull/396), [#398](https://github.com/DevinoSolutions/dokploy-community/pull/398)). Usage: `docs/compose-rolling-replace.md`.

**Security: Traefik file access is confined to the Traefik directory** ([#397](https://github.com/DevinoSolutions/dokploy-community/pull/397), port of upstream Dokploy [#5070](https://github.com/Dokploy/dokploy/pull/5070), with credit to its authors). **Stack environments no longer go through the shell command line** ([#394](https://github.com/DevinoSolutions/dokploy-community/pull/394)). Compose stacks (`docker stack deploy`) embedded their environment in the deploy script, up to three times, so a large environment could fail with "Argument list too long" and the values were visible in `ps`. ### New in v0.30.8-community.25

**Opt-in Compose deploy guardrails** ([#375](https://github.com/DevinoSolutions/dokploy-community/pull/375), issue [#374](https://github.com/DevinoSolutions/dokploy-community/issues/374)). A compose deploy was marked done as soon as `docker compose up` returned, with no readiness check and little in the log to show where the time went (in #374, web was down for about 135 s while the old container was being removed). Three guardrails, configured per compose, are now available. All are off by default, so existing composes deploy exactly as before.
- **Phase timestamps.** Each deploy phase is logged with a UTC timestamp and the seconds elapsed since the previous one.
- **Docker events capture.** While `docker compose up` runs, container lifecycle events (create, start, die, health status) for the project are written to the deploy log. The capture is size-capped and cleaned up by a watchdog if the deploy shell goes away.
- **Health check.** An optional HTTP(S) URL is polled before the deploy is marked done. If it does not return a success status before the timeout, the deploy is marked `error` and the failure notification fires.

To enable them, open the compose service, go to **Advanced** and use the **Deploy guardrails** card. The same settings are available through `compose.update` (`deployGuardrails`).

Limits to know about:
- The events capture covers only `compose up`, not the image pull.
- The health check does not run for swarm stacks, and cannot be saved for one.
- There is no automatic rollback: when the health check fails, the new release is left running so you can inspect it.
- The timeout is wall-clock time for the whole health check, not per request.
- Preview deployments are never guarded, duplicating a compose does not copy its guardrails, and project exports leave out the health check URL unless secrets are included.

### New in v0.29.13-community.2

**Migration reliability for official-Dokploy switchers, credential scrubbing & backup cleanup.** A patch release on the v0.29.13 base — five fixes, no new migrations. **Upgrading is recommended**, especially if you switched to the fork from official Dokploy v0.29.13 or use S3 backups.

- **Migration failures fixed for installs switching from official Dokploy v0.29.13** — installs that moved from official Dokploy v0.29.13 to the fork previously re-ran migration 0174 (the fork re-timestamps it), hit a `duplicate_column` error, and rolled back the **entire** pending migration batch (0174–0192) — leaving every fork table and column silently missing. Migration 0174 now uses `ADD COLUMN IF NOT EXISTS`, a fork-wide migration-idempotency audit plus a static lint test guards against recurrence, and migration failures now log loudly and report to Sentry instead of failing quietly ([#172](https://github.com/DevinoSolutions/dokploy-community/pull/172)).
- **Credentials scrubbed from error reports** — a failed backup command could previously embed live S3 credentials (e.g. rclone `--s3-access-key-id` / `--s3-secret-access-key`) in an error message that then flowed into error reports. Credentials are now scrubbed from `ExecError` messages and from all error reports (a Sentry `beforeSend` scrubber) before anything leaves the process ([#173](https://github.com/DevinoSolutions/dokploy-community/pull/173)).
- **Partial backup uploads are cleaned up on failure** — when a backup fails mid-upload, the truncated partial object is now deleted from the destination, so it can't pollute buckets or evict good backups from retention. Failure diagnostics now distinguish **"Backup failed"** (a dump error, with the dump's stderr) from **"Upload failed"** (a destination error) ([#174](https://github.com/DevinoSolutions/dokploy-community/pull/174), inspired by upstream [#4896](https://github.com/Dokploy/dokploy/pull/4896)).
- **Cursor pointer on buttons** — buttons now show a pointer cursor on hover ([#170](https://github.com/DevinoSolutions/dokploy-community/pull/170), upstream [#4890](https://github.com/Dokploy/dokploy/pull/4890) by @SteadEXE).
- **Security-audit robustness** — the server security audit no longer breaks when sshd/ufw config contains duplicate directives; the grep pipelines take the first match and strip carriage returns so the audit JSON stays valid ([#171](https://github.com/DevinoSolutions/dokploy-community/pull/171), upstream [#4889](https://github.com/Dokploy/dokploy/pull/4889) by @reikjarloekl).

### New in v0.29.12-community.8

**Move services between servers, and organization-wide backup policies.** Two headline features plus one additive migration (0191).

- **Move a service to another server** — move an Application, Compose, or database service to a different server in multi-server mode. The move runs a two-phase **scan → execute** flow with a downtime-safe, **copy-based cutover**: the source is stopped, its data is copied to the destination, and the service's `serverId` switches **only after a fully successful copy** — on any failure the source is restarted and left untouched. No migration ([#148](https://github.com/DevinoSolutions/dokploy-community/pull/148), upstream [#3713](https://github.com/Dokploy/dokploy/pull/3713)).
- **Backup policies + Backup Center** — manage backups organization-wide instead of service by service. Define **policies** scoped to the whole org, specific projects, or specific environments (with a one-click "production environments" preset), covering **database dumps and/or volume backups**, each targeting **one destination** with its own cron schedule and retention. Services added later that match a policy's scope are **auto-covered**. A new **Backup Center** page lists every policy, shows an org-wide **coverage table** (what's backed up vs. not) and the instance backup, and **coexists** with any manual backups you already set up. Redis/applications/Compose are covered via volume backups. Adds additive **migration 0191** ([#153](https://github.com/DevinoSolutions/dokploy-community/pull/153)).

### New in v0.29.12-community.6

**Project favicons, for real — and hardened.** Project icons now resolve the actual favicon of a project's first working domain, and the resolver is locked down against SSRF and stored XSS.

- **Real favicon resolution** — projects without an explicit icon show their first working domain's favicon, including apps that declare it via a custom `<link rel="icon">` path instead of the default `/favicon.ico`; icons now also render in the project switcher, not just cards and headers ([#145](https://github.com/DevinoSolutions/dokploy-community/pull/145)).
- **SSRF hardening** — every URL the resolver fetches, and every redirect hop, is re-validated as same-origin against the originally-requested org-managed host, pinning scheme + host **+ port** so the fetch can't be pivoted to an internal service or another port on the same IP ([#146](https://github.com/DevinoSolutions/dokploy-community/pull/146), [#147](https://github.com/DevinoSolutions/dokploy-community/pull/147)).
- **Stored-XSS hardening** — `image/svg+xml` favicons are rejected (an SVG served with its real content-type can execute inline script), and the icon response carries a locked-down `default-src 'none'; sandbox` CSP plus `nosniff` ([#147](https://github.com/DevinoSolutions/dokploy-community/pull/147)).
- **Private caching** — the auth-gated icon response is now `private`, so a shared cache can't serve one user's favicon to another.
