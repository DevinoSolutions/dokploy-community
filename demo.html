⚠ Pre-demo checklist (do this 60s before)

Two things must be true for the live demo to land cleanly. Verified end-to-end on the test instance, May 2 2026.

A · RESTART dokploy
SSH the host: docker service update --force dokploy
Why: per-server concurrency is read at boot and applied to the BullMQ worker. Live changes to the concurrency value don't propagate to a worker that's already idle-blocked on Redis. A restart guarantees the worker starts at concurrency: 1 from the DB, so Step 3's "Beta = waiting" state actually shows. Without this, Beta runs in parallel and the queueing visual is lost.
B · CONFIRM Remote Test concurrency = 1
Settings → Remote Servers → Remote Test → Deployment Concurrency → 1.
After the restart, the worker reads this and enforces it.
C · Heads-up on the Queue tab
The red Cancel button only appears on the active row, never on waiting rows. (The backend supports cancelling queued jobs via job.remove — it's just not exposed per-row in this UI.) Don't try to cancel the waiting one mid-demo; cancel the active one as Step 4 says.

STEP 3

STEP 4
Click Redeploy on each. Wait for 1/1 running.
STEP 5
SSH the server where demo-net lives (Remote Test = 178.105.8.184) and resolve Alpha's swarm service name from inside an alpine on the same overlay:
ssh root@178.105.8.184 'docker run --rm --network demo-net alpine nslookup concurrency-alpha-dmchad'
Expected output: a non-127.x IPv4 like Address: 10.0.x.y (the swarm-assigned VIP for Alpha on this overlay). DNS by service name works → both apps share an L2 segment.

STEP 6 (UX)
Back on Networks page → delete demo-net while still attached.
Reopen Alpha → orange banner: "1 attachment(s) won't apply" + Remove stale button.
Click it → cleaned up.

⚙ Tech stack & patterns

Concurrency — what's under the hood

  • BullMQ + Redis, per-target queues · queue name deployments for the Dokploy host (LOCAL) and deployments__<serverId> for each remote server. One Worker per Queue; concurrency is read from the DB at boot.
  • Cancel chain: job.remove if waiting/delayed (cheap path) → otherwise AbortController.abort() on the in-flight handler → publish to dokploy:deployments:cancel Redis pub/sub for cross-process consumers → kill-docker-build SIGINT side-channel against the active build subprocess (local pkill or remote-server SSH pkill).
  • Per-target isolation: a busy Remote-Test queue does not block LOCAL host deploys (proven live: 4 deploys running in parallel across 2 queues simultaneously).
  • Boot-time pre-warm: deploymentQueueManager.bootstrap() iterates getAllServers() and ensures a Worker for every server's queue, so jobs persisted in Redis from a previous process are picked up immediately on restart.
  • Job shape unchanged from canary's DeploymentJob type. tRPC routes touched: deployment.queueList, application.cancelDeployment / compose.cancelDeployment (now also call cancelDeploymentsByApplication/Compose + killDockerBuild for the self-hosted path), server.updateDeploymentConcurrency, settings.updateDeploymentConcurrency.
How this differs from the original PR draft: the first cut replaced canary's BullMQ worker with a custom in-memory DeploymentQueueManager class. That worked, but it was a bold architectural move for an upstream PR — it ripped out the persistent queue that survives restarts. The ship-ready version keeps BullMQ and adds a per-target queue layer on top. Net effect: one code path for cloud (no-op) + self-host (real BullMQ), real per-server concurrency, restart-safe (Redis-backed), and abort that genuinely interrupts a build mid-flight via the kill-docker-build SIGINT side-channel.

Networks — what's under the hood

  • New network table + networkIds: text[] column on the 7 swarm-deployable resources (application + 6 DBs)
  • Server-side resolver: resolveNetworkNamesForResource() filters to same-server + overlay-only
  • Builder injects names into the swarm task spec via generateConfigContainer → Networks: mergeNetworks(…)
  • UI: shared ResourceNetworksCard component, dropped into all 7 resource Advanced tabs
  • Stale-attachment auto-detected (network deleted / wrong server / wrong driver) — Remove stale action
Pattern reuse: Based on upstream Dokploy PR #3774 (Mauricio Siu). We extended it with libsql support, organisation scoping, an overlay-only filter (Swarm rejects bridge with HTTP 403), a Postgres 100-arg cap fix on findMountById, and the orphan-cleanup UX. Schema shape, tRPC router naming, and the per-resource update flow all match the existing Dokploy conventions.

Why these PRs feel native to Dokploy

  • Routers: same shape as every other resource router (application, compose, …)
  • UI cards: same Card + CardHeader + CardContent shadcn pattern as the rest of the dashboard
  • Drizzle migrations & snapshots follow the existing numbering / journal convention
  • Swarm task spec injection uses the existing mergeNetworks helper — no new abstractions
